# Capability map

Changes I want to make to my factory, ranked. Started in L2 on Day 1, finished on Day 2 morning, and built from in the three feature labs.

The target is the factory `docs/SOFTWARE_FACTORY_MANIFEST.md` describes: Planner → Architect → Designer → Coder → Reviewer → Deployer, with a human gate after the Architect and another after the Reviewer, and a file written at every stage. The factory that built the MVP is the `base-factory` chain (mayor, polecats, architect, refinery; see `coordination-channels.md`). It shipped all 19 feature beads, but it skipped both human gates and wrote none of the stage files. Each row below closes one part of that gap.

## The layer each change touches

Naming the layer is most of the thinking, because it decides what file you open.

| Layer | You are changing | Shape of the change |
| --- | --- | --- |
| **Agent** | What an agent knows and how it judges | A prompt template, an `agent.toml` |
| **Formula** | What steps a job has and what they depend on | A `*.formula.toml`, often extending an existing one |
| **Order** | When something happens with no human present | An `order.toml` with a `cooldown`, `cron`, `condition` or `event` trigger |

If a change does not fit any of the three, it is probably a change to your *project* rather than to your factory. Write it down somewhere else.

## Where these rows came from

Note the evidence behind each row, so a future you can tell a real finding from a good idea.

- **The gate bounced a bead of mine, and its feedback said:** `fup-oe9.4` was the only architect rejection (loop 1/2): "ADR 0001 rule 2 (every quality gate must work on a clean checkout) fails" because a `PizzaBuilderPage.test.tsx` test ran 1.8–4.5 s against Vitest's 5 s timeout when two full suites ran at once. The same issue still exists on `main` as `fup-vng` (`StaffMenuPage.test.tsx`). This is the root of row 2's "run the criteria on a clean checkout every time".
- **A reviewer produced an opinion rather than a verdict, because it had nothing to cite:** the architect's non-blocking follow-ups on five beads (row 4) were advice with nowhere to go. `fup-h1d` got no opinion at all, because no ADR or review standard the architect reads covers network exposure (row 7). With no design spec, the architect's guidance for `fup-oe9.4` and `fup-oe9.6` came from a sibling bead's notes (row 5).
- **I read a diff the factory wrote and would have written it differently, because:** `usePolling` (`fup-qt5.5`) has no request timeout, so one hung poll stops all later polls and hides the stale banner (`fup-3ex`). A spec that listed the stale-poll state would have required that timeout (row 5). `server/src/index.ts` listens with no host (`fup-h1d`, row 7).
- **Something ran that should not have, or did not run that should have:** neither human gate ever ran: 19 of 19 beads were `merge_strategy=direct` with no `pr_url` (rows 1, 6). Release Criteria 4, 5 and 7 ran once instead of once per feature (row 2). None of the stage files were written: `work-packages/`, `design/`, `review-reports/` and `release-gates/` are all empty on `main` (rows 2, 3, 5, 8). Epic closure and follow-up dispatch never ran (row 4).

## Out of scope, deliberately

Things you decided not to do, and why. This section stops you re-litigating the same idea in three weeks.

- **Six separately named agents, one per manifest role.** The manifest's roles map onto existing agents (see `coordination-channels.md`). Adding a stage means adding its *gate and file*, not renaming an agent.
- **Single shared stage files** (`work-packages/fired-up-pizza.md`, `design/fired-up-pizza-spec.md`, and so on, as the manifest literally lists them). With up to five polecats running in parallel, one file per stage would cause merge conflicts on every bead. Use per-bead files instead.
- **`multi-vendor-rig` and `principles-loop-rig`.** They make the architecture review deeper, but the architecture lane is the one stage that already works: one justified bounce in 19 beads. The gaps are in the stages around it.
- **`review-loop-rig`.** It forces at least one bounce per bead. The architect already bounces when there is a reason, and a forced loop doubles the cost of every bead.
- **CI, a VPS deploy target, or observability.** The manifest rules these out for the MVP. Row 2's release gate runs locally in the refinery's worktree.
- **Fixing `fup-vng`, `fup-3ex`, `fup-h1d`, `fup-cfa`, `fup-hi8` here.** Those are project bugs; they get slung as beads. The factory change is making sure they would be caught earlier (rows 2, 5, 7) and dispatched without a human noticing (row 4).
- **`self-improvement` and `internal-wiki`.** Worth revisiting once rows 1–4 are in. Until there is a review report and release gate file per bead, a daily self-audit would only have bead notes to read.
