## Objective

By the end of this exercise you will be able to refine a blocked bead with the *Grill Me* local-agent skill and re-sling it through the project-manager so it passes on the first try.

## Prereqs

- Page [05.1](./05.1-bead-gate-checks.md) complete: `bead-gate-rig`
  is installed, the project-manager agent is registered, and at
  least one blocked bead exists in the rig (the `i.md` bead from
  05.1 step 5, still blocked if you did not unblock it in step 6).
- A local agent harness with skill support. Examples covered below:
  - **Claude Code** (`~/.claude/skills/<skill-name>/SKILL.md` for
    user-scoped, or `.claude/skills/...` in the repo for
    project-scoped — the latter ships with the rig).
  - **Codex CLI**, **Gemini CLI**, or any harness that loads
    free-form `SKILL.md` files. The skill is harness-agnostic by
    design.
- `git` and a working clone of `https://github.com/mattpocock/skills`
  somewhere local — the skill is one markdown file we are going to
  copy.
- The blocked bead from 05.1, OR a fresh malformed bead you create
  for this page (instructions below).

## Context

Page 05.1 added the project-manager — a gate at the front of the
factory that blocks malformed beads. What 05.1 didn't solve is the
*operator's* side: when a bead is blocked, the human has to rewrite
the bead's title, description, and metadata before re-slinging. Doing
that by hand is tedious and the same blanks tend to come up again
and again ("what's the deliverable here? what file? what's the
acceptance check?").

This page installs a small productivity skill — *Grill Me*, by
Matt Pocock — into your local agent. The skill is just a markdown
file that teaches your agent to interview you, ask the missing
questions, and convert your answers into a tightened bead. Then we
walk one of the malformed beads from page 05.1 through it and re-sling
the project-manager — this time it passes.

There is **no factory-side change** in this page. No new pack, no
new agent, no city restart. The factory already does its job; this
page is about the operator's tools.

The project-manager from page 05.1 is mechanical: it reads what's on
the bead and decides PASS or FAIL. It does not write *for* the
operator. When a bead is vague — "implement X", no description, no
`target_file` — the project-manager's feedback is "your bead is
vague, fix it" and the operator is left staring at `bd update`.

Grill Me flips the interaction. Instead of you sitting in front of a
blank bead trying to remember what to fill in, you tell the local
agent "grill me on `$BEAD`" and the agent asks you the missing
questions one at a time: "What file does this write?", "What does
done look like?", "Which ADR governs this?". Your one-line answers
get composed into a tightened bead description that the
project-manager can pass.

This is a **local-agent-side** improvement, not a factory-side one.
The factory does not know or care that you used Grill Me; it just
sees a better-formed bead arrive at the project-manager.

## Walkthrough

### 1. Install the Grill-Me skill

Grill Me lives at:
`https://github.com/mattpocock/skills/blob/main/skills/productivity/grill-me/SKILL.md`

Clone the skills repo somewhere convenient and copy the `SKILL.md`
into your local agent's skills directory. Pick the install location
that matches your harness.

**copy and paste**

```bash
# Clone (or pull) the skills repo somewhere outside the rig.
git clone https://github.com/mattpocock/skills.git ~/grill-me-skill
# (or `cd ~/grill-me-skill && git pull` if you already have it)
```

**Claude Code (project-scoped — recommended for this tutorial):**

**copy and paste**

```bash
cd "$ASCII_ART_PATH"
mkdir -p .claude/skills/grill-me
cp ~/grill-me-skill/skills/productivity/grill-me/SKILL.md \
   .claude/skills/grill-me/SKILL.md
```

The skill loads when Claude Code starts inside the rig. Project-scoped
install means anyone cloning the rig gets it; the skill is part of
the rig's developer workflow, not your personal config.

**Claude Code (user-scoped — if you want the skill across every
project):**

**copy and paste**

```bash
mkdir -p ~/.claude/skills/grill-me
cp ~/grill-me-skill/skills/productivity/grill-me/SKILL.md \
   ~/.claude/skills/grill-me/SKILL.md
```

**Codex CLI / Gemini CLI / other harnesses:**

The skill is harness-agnostic — it's a free-form markdown file with
instructions. Drop `SKILL.md` into wherever your harness loads
skills (each harness has its own convention; check that harness's
docs). If your harness has no skills primitive, you can also just
read the `SKILL.md` aloud to your local agent at the start of a
session ("here are the rules for the next interaction"). Crude, but
works.

Confirm the skill is loaded by starting your local agent and asking
"do you have the Grill Me skill available?" — the agent should
acknowledge and summarize what it does. In `claude` you can also
see existing skills listed when you type `/` in the prompt window.

### 2. Pick a bead to refine

Either reuse the `i.md` bead from page 05.1 step 5 (still blocked
if you skipped step 6), or create a new deliberately-vague bead for
this exercise.

**Option A — reuse the page 05.1 bead:**

**copy and paste**

```bash
cd $ASCII_ART_PATH
export BAD_BEAD=$(bd list --type=task --status=blocked --limit 0 \
  | grep -E "Implement i\.md$" | awk '{print $2}')
bd show $BAD_BEAD
```

**Expected output**

```text
# status=blocked, bead_review_passed=false,
# bead_review_feedback explains which check failed.
```

**Option B — create a fresh vague bead:**

**copy and paste**

```bash
cd $ASCII_ART_PATH
export BAD_BEAD=$(bd create \
  --type=task \
  --title="rendering thing" \
  --description="" \
  --json | jq -r '.id')
bd show $BAD_BEAD
```

**Expected output**

```text
# A blank-description bead with a vague title. Perfect for grilling.
```

Either way, capture the bead ID in `$BAD_BEAD` for the rest of the
walkthrough.

### 3. Grill the bead

Open your local agent in the rig and trigger the skill. The skill's
exact invocation phrase depends on the harness, but a plain
"grill me on `$BAD_BEAD`" works in most setups.

**Example**

```text
You: Grill me on bead $BAD_BEAD. I want to refine it so the
project-manager passes it.
```

The agent should:

1. Run `bd show $BAD_BEAD` to read what's currently on the bead.
2. Identify the gaps (missing description, missing `target_file`,
   vague title).
3. Ask you focused questions one at a time. Examples:
   - "What file is this writing? Give me the path relative to the
     repo root."
   - "What does the deliverable look like? One sentence is enough."
   - "Is there a parent epic this belongs to?"
   - "Are there any binding ADRs the polecat should respect?"
4. Compose your answers into a draft title and description.
5. Show you the draft, ask for confirmation, then offer to write
   the changes onto the bead via `bd update`.

Sample interaction (yours will vary):

**Example**

```text
Agent: Looking at $BAD_BEAD — title is "rendering thing", description
is empty. Three quick questions:

  1. What file is being written? (Path relative to the repo root.)

You: ascii/i.md

Agent: 2. What's the deliverable? One sentence — what should be in
   ascii/i.md when this is done?

You: An ASCII rendering of the lowercase letter "i" matching the
   style of the other letters in ascii/.

Agent: 3. Is there a binding ADR? (e.g., docs/decision-records/0001.ADR.ASCII.md)

You: Yes, 0001.ADR.ASCII.md.

Agent: Drafted:

  Title: Implement i.md
  Description: Add an ASCII rendering of the lowercase letter "i"
  to ascii/i.md, matching the visual style established by the
  other letters in ascii/. Conform to the rules in
  docs/decision-records/0001.ADR.ASCII.md (Location, File structure,
  ASCII art, Rhyme).
  metadata.target_file: ascii/i.md

  Apply with `bd update`?

You: yes

Agent: Running:
  bd update $BAD_BEAD --title="Implement i.md"
  bd update $BAD_BEAD --description "<paragraph above>"
  bd update $BAD_BEAD --set-metadata target_file=ascii/i.md
  bd update $BAD_BEAD --status=open
  bd update $BAD_BEAD --unset-metadata bead_review_passed

Done. The bead is now eligible for re-review. Run
  gc sling ascii-art/bead-gate-rig.project-manager $BAD_BEAD --on mol-bead-review
to send it through the project-manager.
```

The exact wording depends on the local agent. The shape — a few
focused questions, a draft, an explicit confirm-before-write step —
is the contract Grill Me defines.

### 4. Re-sling the project-manager

After Grill Me has applied the refined bead, re-sling.

**copy and paste**

```bash
cd $FACTORY_PATH
gc sling ascii-art/bead-gate-rig.project-manager $BAD_BEAD --on mol-bead-review
```

Watch:

**copy and paste**

```bash
gc session list
gc session attach <project-manager-session>
# Detach with Ctrl+b then d.
```

Confirm the verdict:

**copy and paste**

```bash
gc bd show $BAD_BEAD
```

**Expected output**

```text
# status=open, bead_review_passed=true,
# gc.routed_to=ascii-art/.../polecat. The polecat pool will pick this up.
```

The project-manager passes on the first sling because the title is
meaningful, the description names a concrete deliverable,
`target_file` is set and consistent with the title, and the parent
epic (if any) is intact.

From here, the polecat / refinery / architect chain runs as in pages
01–04. Wait for the PR and merge as before.

### 5. (Optional) Add the Grill-Me prompt to your team's CLAUDE.md

If your rig has a `CLAUDE.md` (or `AGENTS.md`, or whatever your
harness's project-instructions file is called), drop a one-liner in
it pointing at the skill. Anyone working in the rig — human or AI
agent — sees it on first session start and knows to grill before
slinging.

**Example**

```markdown
## Refining beads

Before slinging a bead at the project-manager, run the **Grill Me**
skill to fill in any obvious gaps (target_file, deliverable
description, parent epic). The skill ships at
`.claude/skills/grill-me/SKILL.md` in this repo.
```

This is optional. The factory does not require it. But on a real
project with multiple operators, a one-line nudge in the project
instructions has more leverage than any pack patch — every new
operator picks it up automatically.

### 6. Reflect

That worked. The project-manager rejected the vague bead in 05.1;
Grill Me walked you through filling in the blanks; the
project-manager passed the refined bead on the next sling. The
factory side is unchanged — same gate, same checklist — but the
operator side now has a tool for refining beads that's faster and
less error-prone than staring at `bd update`.

What's still missing:

- **Refinement is still operator-driven.** The Grill-Me skill is
  Q&A — the human answers the questions. There is no agent that
  *writes* design/test/docs context onto a bead before the
  project-manager sees it. **Hardening 1 — Bead-creation formula
  extensions** introduces additional pre-PM agents (Design Lead,
  Test Lead, Doc Lead) that produce design specs, test plans, and
  docs requirements via formulas, so the project-manager has more
  to check by the time it sees the bead.
- **One ADR + docs corpus on the review side.** The architect
  reviews against a single rig-wide pool of ADRs and current docs.
  **Hardening 2 — Specialize reviewers per domain** splits the
  architect into ADR, design, testing, and docs reviewers running
  in parallel.
- **Solo provider.** Every reviewer agent in the rig runs against
  whichever model your harness pins. **Hardening 4 — Strengthen the
  review system** introduces multi-provider reviewers (Codex,
  Claude, Gemini) with a synthesizer to fuse their verdicts.

## Troubleshooting

- **Local agent doesn't recognize the skill.** Check the harness's
  skills load path. For Claude Code, the project-scoped path is
  `<repo-root>/.claude/skills/<name>/SKILL.md` — note the trailing
  `SKILL.md` filename is literal (uppercase). Restart the harness
  after dropping the file.
- **Grill Me asks the wrong questions.** The skill is small (~50
  lines of markdown). Open the `SKILL.md` and read it; the question
  shape is meant to be customized for your domain. Edit the markdown
  to ask domain-specific questions (e.g., for a Go service rig, ask
  for the package path, the test-file path, etc.). The skill is
  yours to mutate.
- **Grill Me writes the bead via the wrong `bd` command.** Different
  `bd` builds expose `--set-metadata` vs `--metadata` differently.
  Confirm the harness's commands match your `bd` build by running
  one of them by hand first; update the `SKILL.md` if needed.
- **Project-manager still rejects after Grill Me.** Read
  `metadata.bead_review_feedback` again — Grill Me's coverage of the
  checklist may have a gap. Edit `SKILL.md` to ask the question Grill
  Me missed, or ad-hoc fix the bead via `bd update` and re-sling.
- **The `bead_review_passed=true` from a prior failed run is
  short-circuiting the re-review.** The project-manager's
  load-context step exits early when `bead_review_passed=true` is
  already set. After Grill Me edits the bead, run
  `bd update $BAD_BEAD --unset-metadata bead_review_passed` before
  re-slinging — Grill Me's default flow includes this step but
  customized variants may not.
