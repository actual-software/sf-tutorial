## Objectives

By the end of this exercise you will have:
- A minimal Gas City "city" called `factory1`
- Setup pack installed, making the `polecat` (worker) and `refinery` (reviewer) agents available to `factory1`

## Prereqs

- `gc` 1.1.0+ (run `gc version`)
- `bd` 1.0+ (run `bd --version`)
- `gh` 2.x authenticated to a GitHub account that can create repos (`gh auth status`)
- `git`
- macOS or Linux with `tmux` available
- You've read the [README](../README.md), so you know what you're building

**Copy and paste**

```bash
gc version
bd --version
gh --version
git --version
gh auth status
```

Don't reinstall what you already have. Confirm versions, and if any are missing, follow the upstream install docs:

- `gc`: https://github.com/gastownhall/gascity (install instructions in the project README)
- `bd`: https://github.com/steveyegge/beads
- `gh`: https://cli.github.com/
- `git`: https://git-scm.com/downloads

## Context

We're starting with a simple 2-agent factory and workflow included with Gas City. The first agent will do work; the second will peer review its work and accept or reject. The next page ([00.2](./00.2-setup-foundation.md)) registers the `ascii-art` rig — the project we'll work on for our examples.

Run every step from a working directory you're happy to keep around — the city and (next page) the rig will live as sibling directories under it. Recommended:

**Directory tree**

```text
~Projects/
 └── software-factory-intensive/      # Create this. Rename it later if you want.
     ├── sf-tutorial/                 # Clone the tutorial repo here.
     ├── factory1/                    # Next Gas City will put this here via `gc init ...`
     ├── ascii-art/                   # Then Gas City will put this here with `gc rig add ...`
     └──── <your projects>            # You can add your projects here.
```

## Walkthrough

### 1. Create factory1

Create the `factory1/` directory with an auto-generated `city.toml` and `pack.toml`.

**Copy and paste**

```bash
cd path/to/software-factory-intensive
gc init factory1
```

Follow the interactive prompt. Select:

- **minimal** config template (`1`)
- Claude Code (recommended) or whatever provider you are using

**Copy and paste**

```bash
cd factory1/ && ls
```

**Outcome:** `factory1/`, `factory1/city.toml`, and `factory1/pack.toml` exist.

Initialize a local git repository in `factory1/` and commit the scaffold so you have a personal history of your city's configuration as you work through the tutorial.

**Copy and paste**

```bash
git init
git add .
git commit -m "Initial commit: factory1 scaffold from gc init"
```

> **Note:** This repo is for your local use only. Gas City shares reusable functionality (agents, formulas, prompts) through **packs**, not git. Distribute your customizations by publishing or referencing packs — don't expect others to pick them up by cloning this repo.

Now start the city under the machine-wide supervisor. `gc init` only writes config files — nothing is running yet.

**Copy and paste**

```bash
gc start
```

This registers `factory1` with the supervisor, installs the launchd/systemd service if needed, starts the supervisor process, and brings up the city's Dolt server and agents. **From here on, the supervisor owns the Dolt server's lifecycle for `factory1` — don't run `bd dolt start` yourself** (see [Troubleshooting](#troubleshooting) if you hit Dolt errors).

Run `gc` commands to observe the status of the factory.

**Copy and paste**

```bash
gc status
gc session list
```

**Expected output**


For future use, let's add FACTORY_PATH to the environment variables.

**Copy and paste**

```bash
export FACTORY_PATH="$(pwd)"
```

### 2. Review the setup pack installation

The pack is on disk and your city imports from the setup pack's `pack.toml` — that's what makes the agents "available" in factory1 and its rigs. Inspect the import blocks:

**Copy and paste**

```bash
cat pack.toml
```

**File contents**

```toml
[pack]
name = "factory1"
schema = 2

[[agent]]
name = "mayor"
prompt_template = "agents/mayor/prompt.template.md"

[[named_session]]
template = "mayor"
mode = "always"
```

Now run the `gc doctor` command to check the city's health.

**Copy and paste**

```bash
gc doctor
```

You will see a number of checks run, where "✓" means a pass, "⚠" means warning, and "✗" means an error.

In this case, we see one warning about a legacy import format.

**Expected output**

```text
 ⚠ v2-agent-format — legacy [[agent]] tables found in pack.toml
      hint: run "gc doctor --fix" to rewrite safe mechanical cases, then rerun "gc doctor"
```

We need to remove the agent definition from `pack.toml` since agents are now auto-discovered by the `gc` runtime.

**Copy and paste**

```bash
sed -i '' '/^\[\[agent\]\]$/,/^$/d' $FACTORY_PATH/pack.toml
```

Now run `gc doctor` again to verify the warning is gone.

**Copy and paste**

```bash
gc doctor
```

**Expected output**

```text
gc doctor
✓ v2-agent-format — no legacy [[agent]] tables found
```

Later pages of this tutorial customize behavior on top of the basic city configuration. When you need to alter the agent set, you can either alter these configuration files or override individual agents in your own pack.toml.

### 3. Review the `city.toml` file

View the minimal template's `city.toml`:

**Copy and paste**

```bash
cat city.toml
```

**File contents**

```toml
[workspace]
provider = "claude"
```

### 4. Confirm Dolt is supervisor-managed

When `gc start` brought up the city, the supervisor also started the city's Dolt server. You don't need to start Dolt manually — the supervisor handles its lifecycle for as long as the city is running.

Verify there's exactly one Dolt process for `factory1` and that `bd` can reach it:

**Copy and paste**

```bash
ps aux | grep "dolt sql-server" | grep factory1 | grep -v grep
bd list
```

You should see one `dolt sql-server` process started with `--config .../factory1/.gc/runtime/packs/dolt/dolt-config.yaml`. `bd list` should return without error (likely "No issues found." for a fresh city).

> **Important — do not run `bd dolt start` while the city is supervisor-managed.** It will start a second Dolt that holds a write lock on the same data directory, and the next time the supervisor restarts the city it won't be able to bring up its own Dolt. The `dolt.auto-start` setting in `.beads/config.yaml` only matters for standalone `bd` use outside a running city — the supervisor manages it on its own and may rewrite this value.

### 5. Install the setup pack into factory1

The minimal city you created in step 1 only has the `mayor` agent. The setup pack (`sf-tutorial/artifacts/packs/setup/`) adds the worker (`polecat`) and reviewer (`refinery`) agents that the rest of this tutorial relies on. Install it as a city-level import. Run from inside `factory1/`:

**Copy and paste**

```bash
gc import add ../sf-tutorial/artifacts/packs/setup
```

This copies the pack into `factory1/.gc/system/packs/setup/` and records it in `pack.toml` / `packs.lock`.

Tell the running supervisor to pick up the new pack without a full restart, then confirm the import landed:

**Copy and paste**

```bash
gc reload
gc import list
```

`gc import list` should show `setup` among the active imports. If you don't see it, see [Troubleshooting](#troubleshooting).

## Troubleshooting

### `gc status` shows `Controller: stopped` and `bd` says "Dolt server unreachable at 127.0.0.1:0 ... auto-start is disabled"

You ran `gc init` but not `gc start`. The city's files exist on disk but nothing is running. Run `gc start` from inside `factory1/`. Don't run `bd dolt start` to "fix" this — it creates a different problem (see next item).

### `gc start` fails with `dolt server could not start via gc helper`

Open `.gc/runtime/packs/dolt/dolt.log`. The most common cause is:

```text
database "dolt" is locked by another dolt process; either clone the
database to run a second server, or stop the dolt process which
currently holds an exclusive write lock on the database
```

Another Dolt process is holding the lock on `.beads/dolt/`. Usually it's a leftover `bd dolt start` from an earlier session — note that `bd dolt stop` does not always terminate the process. Find and kill the orphan:

**Copy and paste**

```bash
# All running dolt sql-server processes
ps aux | grep "dolt sql-server" | grep -v grep

# For each PID that does NOT have --config .../.gc/runtime/...
# (i.e., is not the supervisor's), check what data dir it holds:
lsof -p <PID> | grep cwd

# Kill any orphan whose cwd points at a .beads/dolt directory
# you're not actively using:
kill <PID>
```

Then re-run `gc start` (or wait ~10s — the supervisor retries automatically).

### `bd` commands fail with `database "hq" not found on Dolt server`

The Dolt server is running but the `hq` database wasn't created in it. `bd bootstrap` sometimes reports success without actually creating the database. Quickest recovery in a supervisor-managed city:

**Copy and paste**

```bash
gc stop
cd .beads/dolt && dolt sql -q "CREATE DATABASE IF NOT EXISTS hq;" && cd -
gc start
```

After `gc start` brings the city back up, run any `bd` command (e.g., `bd list`) — bd will auto-create the schema tables inside `hq` on first connection.

### Recurring breakage after reinstalling `gc` or `bd`

Reinstalling the binaries does not kill running Dolt processes. Check for orphans before retrying:

**Copy and paste**

```bash
ps aux | grep "dolt sql-server" | grep -v grep
```

Anything pointing at a project you're not actively using (especially older paths from before you renamed directories) is safe to kill. Leave alone: the supervisor-managed Dolt for cities you're using (started with `--config .../.gc/runtime/...`) and any standalone `~/.dolt-server` you set up intentionally.
